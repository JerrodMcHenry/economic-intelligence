# ADR-025: Recorded State History Persists an Append-Only Row Per Genuinely-Executed Canonical Computation, Keyed to the Owning `ReleaseCheckRun`, Never a Reconstruction and Never Gated on Whether the State Changed

## Status
Accepted

## Context

Through Increment #25C, `ReleaseAnalysisUpdate` (#18) was this project's only durable trace of a canonical monitor computation's own consequence — and it is, by design, change-only: a check that recomputes Inflation's or Labor's top-level state and finds it identical to before writes zero rows there (`app/db/models.py`'s own docstring: "a check run producing zero analytical consequences... simply has zero rows here, never a synthetic 'no change' row"). #24A's own audit and #25B's own operational-design contract both independently named the resulting gap precisely: no durable row anywhere proves "EI recomputed and confirmed COOLING at time T" for the — common — case where nothing changed. #25B deliberately deferred solving this (§35/§43 there: "OPTION A — #25C is automation only"), reasoning that persistence built before a reliable automated cadence existed would only produce a second, equally gap-prone table. #25C shipped that reliable cadence. #25D (`docs/product/recorded-state-history-v1.md`) is the resulting, fully-worked contract freeze this ADR now implements.

This project has one long-standing architectural principle directly at stake here: **facts are sourced, calculations are deterministic, AI is interpretive** — and, specifically for this feature, a corollary #24A/#24B already established for State Duration and now extends to recorded history: **a value computed today from today's data is a reconstruction; a value EI durably wrote at the moment it was computed is a recording — the two must never be conflated, and only the second is a genuinely non-reproducible asset** (#24A §35).

## Decision

**A new table, `recorded_monitor_results`, stores one immutable row per genuinely-executed canonical monitor AFTER result — written whenever, and only whenever, `_evaluate_component_at("PRIMARY_MOMENTUM")`/`_evaluate_labor_at` actually runs inside `ReleaseProcessingService._apply_changes_and_compute_analysis`, regardless of whether the resulting state differs from before.** Concretely:

- **One rule, not two, governs recording.** The exact same condition that makes the AFTER call run at all (an observation change that maps to a canonical component) is the only condition that creates a row. This single rule simultaneously implements both required behaviors: a genuine recomputation that confirms an unchanged state IS recorded (the entire point of this feature); a `NO_CHANGE` check that never reaches the AFTER call at all is NOT recorded (never a fabricated computation event).
- **The write happens at the existing, unmodified computation point — never a second, independent calculation.** `_apply_changes_and_compute_analysis` already computes this exact AFTER evidence for `ReleaseAnalysisUpdate`'s own diffing; this ADR's own row is built from that same in-memory value, returned as a second, small return value from the same function, and persisted by `process_occurrence` immediately after the existing `check_run = repo.add_check_run(...)` call obtains a real id — the identical point `add_observation_update`/`add_analysis_update` already wait for. `ReleaseCheckRun`'s own creation order, meaning, and timing are completely unchanged.
- **Identity is `UNIQUE(release_check_run_id, monitor, evaluation_period)` — never `(monitor, evaluation_period, methodology_id)`.** The latter would collide across every legitimate repeat (a later release, a provider revision reprocessing the same period, a manual retry). Keying identity to the specific, always-unique `ReleaseCheckRun` that produced it is what lets the same period be legitimately, honestly recorded again and again over time without ever silently overwriting an earlier row.
- **Append-only through normal application code.** The repository exposes exactly one write method, `add_recorded_monitor_result` — mirroring `ReleaseObservationUpdate`/`ReleaseAnalysisUpdate`'s own repository, which likewise expose only `add_*` methods. No update, upsert, or delete path exists anywhere in application code. A later provider revision or methodology change never mutates an existing row; it produces an entirely new one.
- **`calculated_at` reuses the owning `ReleaseCheckRun.completed_at` value verbatim — no independent clock read.** All AFTER-evidence computation for one occurrence happens synchronously, inside one transaction, before that single timestamp is captured; reusing it for every row a given call writes is simpler and more honest than pretending sub-transaction timing precision this product has no use for.
- **State-only, not a full monitor snapshot.** The persisted quartet — `state`, `evaluation_period`, `methodology_id`, `data_basis` — is deliberately the same minimal shape as the response contract State Duration V1 already uses, not the full `InflationMonitorResult`/`LaborMonitorResult` object. No evidence, no metric detail, no JSON escape hatch — every column is a plain, typed scalar, extending (not exempting) ADR-022's own "no full monitor snapshot" discipline for #18, with this table named as the one deliberate exception, allow-listed by name in that guard rather than the guard being loosened.
- **`ReleaseCheckRun` alone is provenance — `MaintenanceSweep` is deliberately never referenced.** No `sweep_id` is threaded into `process_occurrence`'s own signature; manual CLI processing, which has no sweep at all, must produce equally valid, equally complete records as automated processing. Provenance describes *what computation ran*, never *what scheduled it*.

## Alternatives Considered

- **Record only on state change, reusing `ReleaseAnalysisUpdate`'s own trigger.** Rejected: this is precisely the status quo the whole feature exists to fix — it would produce a second table with the exact same gap the first one already has.
- **Record on every check run, regardless of whether canonical computation ran.** Rejected: would fabricate a computation event for `NO_CHANGE` checks that never touched the domain layer at all — a direct violation of "actually calculated" (contract §6), and would make the table's own existence claim something false.
- **Identity keyed to `(monitor, evaluation_period, methodology_id)` only, upserting on repeat.** Rejected: destroys exactly the temporal evidence this feature exists to preserve — a later request for "what did EI record for August" would silently return only the most recent view, never the full, honest history of how EI's own understanding evolved.
- **A dedicated, separate repository for `RecordedMonitorResult` (mirroring `MaintenanceRepository`'s own precedent).** Rejected in favor of extending `ReleaseProcessingRepository`: unlike `MaintenanceSweep` (a genuinely different-shaped, independently-transactioned concept), `RecordedMonitorResult` shares its transaction, its FK, and its closest sibling tables' (`ReleaseObservationUpdate`/`ReleaseAnalysisUpdate`) own existing repository placement — the more precedented, more consistent choice once inspected directly against current code, not assumed from a "likely dedicated repository" prior.
- **Restructuring `process_occurrence` to create `ReleaseCheckRun` earlier, before analysis, to simplify FK sequencing.** Rejected: unnecessary. `ReleaseCheckRun` already obtains a real id at the correct point in the existing sequence (after analysis, via an existing flush); threading the already-computed recordable results forward one step, rather than moving the check-run creation backward, achieves the same result with zero change to `ReleaseCheckRun`'s own established meaning and timing.
- **Persisting metric/evidence detail alongside state (a fuller snapshot).** Deferred, not rejected outright: real auditability value, but genuine scope expansion this contract explicitly keeps out of V1 (state-only), especially since metric-level fidelity without a genuine input-vintage system would not achieve true point-in-time reproducibility anyway (see "Consequences" below).
- **Bundling this persistence into #25C itself.** Already rejected once, explicitly, in #25B (§35/§42/§43) — sequencing this after a reliable automated cadence existed so the resulting asset is comprehensive rather than gap-prone from day one.

## Why This Decision

The single governing rule — record exactly when, and only when, the AFTER computation genuinely runs — is what makes this feature simultaneously simple to implement (a second return value from an already-existing call, not a new domain computation) and impossible to misuse into a false claim (it structurally cannot record a computation that never happened). Keying identity to the owning `ReleaseCheckRun` rather than to the (monitor, period) pair alone is the one design choice every other property of this feature depends on: it is what makes repeated, legitimate recalculation of the same period an expected, valued behavior rather than a collision to work around.

## Consequences / Tradeoffs

- Gains: closes the single most-cited gap across #24A, #25A, and #25B — a durable, non-reproducible record of what EI's own canonical computation concluded, at the moment it concluded it, distinct from any later reconstruction of the same period under revised data or a later methodology version.
- Gains: zero new economic logic anywhere — every persisted value is copied verbatim from an already-existing, already-tested domain function's own return value; `app/domain/inflation.py`/`labor.py` are untouched.
- Gains: manual and automated processing produce identical recorded history with zero special-casing, inheriting #25C's own "one safe path, never two" discipline for a third capability (locking, crash-safety, and now recording) without any of them needing to know about each other.
- Cost: state-only persistence cannot, by itself, prove which exact input values produced a given recorded state — reconstructing the precise numeric inputs behind an old recorded row still depends on `EconomicObservation`'s own in-place-overwrite behavior, which this ADR does not change. A recorded state is trustworthy evidence of EI's own output; it is not a vintage-data system.
- Cost: no correction/invalidation mechanism exists yet — a genuine software defect that produced an incorrect historical row requires a controlled, out-of-band database correction, not an in-application fix, for as long as V1's scope holds.
- Cost: recording is invisible to any consumer until a future read API or UI is built on top of it — this ADR provides the asset, not (yet) the way to see it.

## Revisit When

- A future increment builds a read API or Since Last Visit on top of this table — at that point, confirm the query/index shape already provisioned (`(monitor, calculated_at)`, `(monitor, evaluation_period)`) is actually sufficient for the real access pattern that emerges, rather than assuming the contract's own forward-looking description was exactly right.
- A genuine second methodology version ships for either monitor — at that point, confirm every consumer of this table correctly groups or filters by `methodology_id` rather than assuming a query's results share one methodology, exactly as this ADR's own decision requires but cannot enforce at the schema level alone.
- A real correction/invalidation need arises (a genuine software defect discovered in already-recorded rows) — at that point, design the minimal `invalidated_at`/`superseded_by`-shaped mechanism this ADR deliberately deferred, rather than allowing ad hoc database edits to become a normal, undocumented practice.
- Metric/evidence-level auditability becomes a real, named product requirement — at that point, this ADR's own schema is confirmed extensible via an additive sibling table keyed by `recorded_monitor_result_id`, never by widening this table's own columns.
