# ADR-008: Alembic for Schema Migrations

## Status
Accepted

## Context

Once ORM models exist (`app/db/models.py`), there needs to be a way to get
their shape into an actual PostgreSQL database — and, going forward, to
evolve that shape over time without losing a record of how it changed or
risking a schema drift between environments.

## Decision

Use **Alembic** for all schema changes. The initial migration
(`alembic/versions/6412695f6f9d_*.py`) was generated with
`alembic revision --autogenerate` against the ORM models, reviewed by
hand, and applied with `alembic upgrade head`. Application startup never
calls `Base.metadata.create_all()`.

## Alternatives Considered

- **`Base.metadata.create_all()` at application startup.** The simplest
  possible option — SQLAlchemy inspects the current model classes and
  creates any missing tables. Rejected as the ongoing schema-management
  strategy: it has no concept of *changing* an existing table (adding a
  column, changing a constraint) without manual, undocumented
  intervention, and it leaves no history of how the schema got to its
  current shape — "the schema" is just whatever the Python models say
  *right now*, with no reviewable diff when they change and no reliable
  way to reproduce a specific past schema state.
- **Manual SQL scripts, run by hand.** Explicit and reviewable in
  principle, but with no tooling enforcing that they're applied in order,
  applied exactly once, or that a downgrade path even exists.

## Why This Decision

Alembic keeps schema evolution and application code evolution as two
histories that stay in sync deliberately: every schema change is a
committed, ordered, reviewable file with both an `upgrade()` and a
`downgrade()`, and `alembic upgrade head` is the one command that brings
any environment's database to the schema the current code expects.
Autogeneration is used as a *starting point*, not a black box — the
initial migration was read against the actual ORM models to confirm the
primary keys, the foreign key's `ON DELETE CASCADE` behavior, both unique
constraints, and nullability all came out as intended before it was
applied.

## Consequences / Tradeoffs

- Gains: a reviewable, ordered history of schema changes; a `downgrade()`
  path defined alongside every `upgrade()`; one command
  (`alembic upgrade head`) to bring any environment's schema current;
  the real `DATABASE_URL` is sourced from application config at migration
  time (`alembic/env.py`), so no credential needs to live in `alembic.ini`.
- Cost: schema changes now require an explicit step (generate, review,
  apply a migration) instead of just editing a model class and restarting
  the app. This is friction on purpose — it's the mechanism that makes
  schema history exist at all.
- Cost: autogenerated migrations aren't automatically correct — they
  still require the same human review any generated code does; this ADR
  and the journal both record that the first migration was read and
  checked, not merely run.

## Revisit When

- Migration volume or team size grows enough that migration conflicts
  (e.g. two people generating migrations off the same base concurrently)
  become a real coordination problem — not a concern at this project's
  current single-developer, single-branch stage.
- A need arises for data migrations (backfilling/transforming existing
  rows), not just schema migrations — Alembic supports this already
  (arbitrary Python in a migration's `upgrade()`), so this is a usage
  pattern to adopt when needed, not a reason to reconsider the tool.
