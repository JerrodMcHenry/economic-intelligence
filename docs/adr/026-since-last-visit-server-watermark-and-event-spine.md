# ADR-026: Since Last Visit Uses a Server-Captured-Before-Query Watermark and `ReleaseCheckRun` as Its Event Spine, Never a Generic Event Ledger

## Status
Accepted

## Context

Through Increment #25E, Economic Intelligence had, for the first time, a durable, non-reproducible record of what its own canonical computation concluded and when — but nothing surfaced it to a user. #25A's own retention audit named RETURN as the single missing link in the product loop; #25C (automated checking) and #25E (recorded results) were the two prerequisites that audit itself identified as needing to land first. #25F (`docs/product/since-last-visit-v1.md`) is the resulting, fully-worked product contract; this ADR records the one architectural decision from it most consequential for any future increment building on the same read model: how a client-supplied checkpoint is compared against server-side event history without either losing events to a race condition or inventing new, generic infrastructure to do it.

Two hard constraints shaped this decision, both already established elsewhere in this project and reused rather than re-derived: **facts are sourced, calculations are deterministic** (this feature computes nothing new — it categorizes already-persisted rows) and **no server-local/browser-local clock may be treated as authoritative for cross-request event ordering** (the same discipline #25C's own `as_of_date` threading already established for a different consumer).

## Decision

**A single server-captured `through` watermark, taken from `datetime.now(timezone.utc)` exactly once, before any query executes, is the sole authority for "what has EI recorded so far" — never a value the browser computes or supplies. `ReleaseCheckRun` is the event spine every other table's rows are joined through — no new, generic "event"/"activity" table is created.** Concretely:

- **`through` is captured first, always.** The window query is `ReleaseCheckRun.completed_at > after AND completed_at <= through`. Capturing `through` before running any query — rather than after, or from a "response-finished" timestamp — is the one detail that makes the whole design race-safe: a commit landing between that capture and the response finishing necessarily has `completed_at > through`, so it is excluded from the *current* response but is guaranteed to have `completed_at` less than or equal to the *next* request's own `through` (since the client's next `after` becomes this response's `through`) — no event is ever silently, permanently lost, proven directly against a real, separately-committing PostgreSQL session, not merely asserted.
- **`ReleaseCheckRun` is the spine.** `ReleaseObservationUpdate`, `ReleaseAnalysisUpdate`, and `RecordedMonitorResult` all already carry `release_check_run_id` — filtering the spine table by `completed_at` first, then joining out to exactly the selected runs' children, turns what the source contract itself named as a genuinely hard cross-table ordering problem into a single-table one, with zero schema change and zero new generic ledger.
- **A genuine first visit is bounded, never unbounded.** The effective query boundary (`resolve_window`'s own `effective_after`) is always a real, 90-day-bounded value — even when no prior checkpoint exists at all. Only the *response's* own `after` field reports `None` on a first visit, a presentation fact kept deliberately distinct from the real query boundary that governs correctness. This distinction was not obvious from the contract's own prose alone — a first implementation let `None` leak into the repository as a genuinely unbounded lower edge, caught by an end-to-end integration test before verification, not shipped; recorded here so a future reader understands why the two concepts (`effective_after` vs. response `after`) are kept structurally separate rather than collapsed into one field.
- **One current-result-selection rule governs both structural change and unchanged confirmation.** Within one `(release_check_run_id, monitor)` group, only the row with the maximum `evaluation_period` represents the group's own "current" fact — the direct fix for the exact multi-evaluation-period over-surfacing risk #25E's own test suite discovered empirically (one Labor benchmark revision producing up to six `RecordedMonitorResult` rows across propagated periods). Applying the identical rule to both `ReleaseAnalysisUpdate`-derived structural changes and `RecordedMonitorResult`-derived unchanged confirmations, rather than inventing two different selection rules, keeps the two tiers symmetric and auditable against one shared, simple principle.
- **Coverage (`CHECKED`/`GAP`/`UNKNOWN`) is derived exclusively from persisted evidence, never from code existence.** `CHECKED` requires only genuine settlement (`ReleaseCheckRun` status, reusing #25C's own already-frozen definition verbatim) — it does not require `MaintenanceSweep` evidence at all, so a domain covered entirely by manual CLI processing is honestly `CHECKED`. `MaintenanceSweep` evidence is consulted only to distinguish `GAP` (the worker ran, a specific release simply didn't settle) from `UNKNOWN` (no evidence the worker ran at all) — restating, for a new surface, #25B's own already-frozen "worker health and economic freshness are separate concepts" rule.

## Alternatives Considered

- **A browser-supplied `after`, compared directly against the server's own "now" at response time.** Rejected: this is precisely the race condition the source contract named explicitly — capturing the boundary *after* querying (or trusting a client clock at all) can permanently lose an event that committed in the narrow window between query execution and response completion.
- **A compound cursor (timestamp + monotonic id) or an opaque server-issued token.** Evaluated and rejected as unjustified complexity: `ReleaseCheckRun.completed_at` is already a real, server-captured wall-clock value (the same kind of value the watermark itself is), so comparing "server clock to server clock" carries none of the cross-source drift risk a browser-supplied value would — a plain timestamp, captured first, is already race-safe without a compound structure.
- **A new, generic `event_log`/`activity` table, populated by triggers or application code whenever something user-relevant happens.** Rejected, explicitly, per the source contract's own instruction: `ReleaseCheckRun` already serves as a real, existing, sufficient spine once its own children are properly joined through it — a generic ledger would duplicate information already durably recorded elsewhere, in a shape nothing else in this project needs, purely to serve one read model.
- **Deriving coverage from whether `app.services.maintenance`/automation code exists in the deployed application.** Rejected: automation-*capable* is not automation-*active* — #25B's own already-frozen distinction, restated here for the identical reason: only persisted `MaintenanceSweep` rows can prove a sweep genuinely ran.
- **Showing every propagated-period row from a revision as its own current-state item.** Rejected: produces exactly the audit-log-shaped noise the source contract names as an explicit anti-goal, and would misrepresent a historical-revision detail as a fresh, current development.

## Why This Decision

The watermark-before-query ordering is the one property every other correctness guarantee in this feature depends on — get it wrong, and no amount of correct categorization logic downstream would prevent silent event loss. Choosing `ReleaseCheckRun` as the spine, rather than inventing new infrastructure, is the same "reuse what already proves the fact, never build a second, parallel truth source" discipline this project has applied at every prior persistence decision this session (#25C's advisory lock reusing existing transaction semantics; #25D/#25E's `RecordedMonitorResult` keying off `ReleaseCheckRun` rather than inventing its own identity scheme).

## Consequences / Tradeoffs

- Gains: the entire read model requires zero new schema — every table it touches already existed before this increment, and the one new capability (a cross-table time-windowed recap) is achieved through query composition, not new persistence.
- Gains: race safety is a structural property of the design (capture-then-filter), not something achieved through locking, retries, or client-side reconciliation logic.
- Gains: a future consumer needing "what changed since timestamp X" for a different purpose can reuse the identical spine-and-watermark pattern without this ADR's own decision needing to be re-litigated.
- Cost: the 90-day lookback bound is a genuine, if disclosed, information limit — a user returning after a longer absence sees a clamped window, not the true full gap, by design (a deliberate scope choice, not an oversight, and one this ADR does not itself decide — see the product contract's own §50-51).
- Cost: coverage's own `GAP`/`UNKNOWN` distinction depends on `MaintenanceSweep` rows existing at all — a deployment that never ran automation (#25C) at any point in a domain's history will show `UNKNOWN` coverage for that domain indefinitely, even if every relevant release happens to be settled via manual processing alone in some other window (settlement itself still correctly reports `CHECKED` independently, per this ADR's own §40 design — this cost is narrower than it first appears, but is named here for completeness).

## Revisit When

- A future account-backed version moves the checkpoint server-side — at that point, confirm the identical `(after, through]` watermark semantics still apply unchanged, with only the checkpoint's own storage location changing (the product contract's own §98 already anticipates this; this ADR's own event-spine and watermark-capture-order decisions require no change either way).
- A second methodology version ships for either monitor — at that point, confirm every consumer of this read model correctly treats mixed-`methodology_id` windows as non-comparable, never silently averaging or collapsing them (the product contract's own §114-115 already names this; this ADR's own spine-based query shape does not itself need to change).
- Historical-revision-propagation detail (deferred by the product contract, §68-71) becomes a real, demanded feature — at that point, confirm whether the current-result-selection rule this ADR froze (max `evaluation_period` per run+monitor) should gain a sibling query for the deferred, older-period rows, rather than being redesigned.
- A genuinely distributed, multi-instance deployment of this service becomes real — at that point, confirm the single-clock-read watermark capture still holds under multiple concurrent request-handling processes (it should, since each request captures its own `through` independently and the race-safety argument does not depend on a shared in-process clock), but this has not been tested under that specific topology.
