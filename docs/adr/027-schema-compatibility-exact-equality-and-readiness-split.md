# ADR-027: Schema Compatibility Is Checked by Exact Revision Equality, Exposed Through a Health/Readiness Split, and Shared Verbatim by the Web Process and Both Operational CLIs

## Status
Accepted

## Context

Increment #26A's live product audit reproduced a real incident: the running application's own code expected the `recorded_monitor_results` table (Alembic head `f5420059a092`), but the database it was pointed at was one migration behind (`09f4c0959e9f`) — the table did not exist, and `GET /api/v1/since-last-visit` returned a live `500`. `/health` reported `200 ok` throughout, because it checks nothing beyond process liveness. 1,463 backend tests passed throughout, because `tests/conftest.py`'s own session-scoped `_apply_migrations` fixture always migrates the isolated test database to head before any test runs — proving application code correctness against a schema the test harness itself guarantees is current, never proving that any specific, real, already-deployed instance's own database agrees with the code at all. This was not a first occurrence: the engineering journal records an earlier increment finding the same development database behind an even older revision, resolved the same way — an operator-approved, ad hoc `alembic upgrade head`.

`docs/product/production-reliability-deployment-v1.md` (#26B) is the resulting, fully-worked operational contract; this ADR records the one decision from it most consequential for how the rest of this codebase must be built to remain compatible: how a running instance determines whether it is safe to serve traffic or process economic data, expressed as durable architecture rather than product narrative.

## Decision

**A running instance's database schema is compatible with that instance's own code only when the database's current Alembic revision exactly equals the revision the packaged application's own migration graph declares as head — computed once, read-only, by one shared function (`app.core.schema_compatibility.check_schema_compatibility`), never duplicated.** Concretely:

- **Expected revision is derived from the packaged migration files themselves** (`alembic.script.ScriptDirectory.get_heads()`), never a manually duplicated hard-coded revision string — the migration files on disk are the one source of truth for "what does this code expect."
- **Actual revision is read via one plain, read-only `SELECT version_num FROM alembic_version`** against the application's own configured database — never `alembic upgrade`/`downgrade`, never `Base.metadata.create_all()`, never any DDL of any kind. A missing `alembic_version` table, an empty one, more than one row, or an unreachable database are each their own distinct, honestly-classified outcome (`SCHEMA_UNINITIALIZED`/`SCHEMA_AMBIGUOUS`/`DATABASE_UNAVAILABLE`) — nothing is ever guessed.
- **V1 compatibility is exact equality, not a range.** Justified by this project's actual current shape (a single developer, a single environment, no rolling deploys, every migration to date purely additive) — not chosen by default. The database's own current head is a strict superset of what any single, currently-running application version needs, so equality loses nothing today; the moment a future migration removes something an old version depends on, or more than one application version may run concurrently against one database, this must generalize to a minimum-compatible-revision range (expand/contract).
- **Health and readiness are two different questions, answered by two different routes.** `GET /health` (unchanged, pre-existing) answers only "is this process alive" — no database call, ever, and it deliberately stays `200 ok` even while the schema is incompatible. `GET /readiness` (new) answers "is it safe to route real traffic here" — database reachability plus schema compatibility plus required configuration, nothing more; it never calls FRED or any external provider (data freshness and request-serving readiness are different concepts, exactly as `automated-economic-maintenance-v1.md` already separated worker health from economic freshness for a different surface). A schema mismatch reports `503` with a public-safe reason and the expected/actual revision strings — it never crashes the process and never causes web startup to fail.
- **The web process's own startup never mutates schema, and never runs the compatibility check at import time either** — `/readiness` evaluates the check lazily, per request, the same way `/health` has always evaluated nothing at all. Nothing resembling a startup hook was added.
- **The maintenance worker performs the identical check, before anything else, reusing the same function** — not a second, independently-written check. `app.operations.run_maintenance` and `app.operations.process_release` each call `check_schema_compatibility()` immediately after their own existing configuration-presence checks and before constructing a `FREDClient` or touching `ReleaseProcessingService`/`MaintenanceOrchestrator` — an incompatible schema performs zero economic processing, creates zero `MaintenanceSweep`/`ReleaseCheckRun`/`ReleaseObservationUpdate`/`ReleaseAnalysisUpdate`/`RecordedMonitorResult` rows, and exits using each CLI's own already-established exit-code convention (`run_maintenance` already had a distinct "fatal/configuration failure" exit code `2`; `process_release` had never had one beyond its own uniform `1`, and gained no new value — a schema mismatch there is treated exactly like its own already-existing missing-configuration case).

## Alternatives Considered

- **A minimum-compatible-revision range, or an explicit compatibility range, for V1.** Rejected: both solve a problem (tolerating either an older or a newer schema than exact head) this project does not have yet, at the cost of tracking an extra value with no current consumer. Deferred explicitly to whenever rolling deploys or a destructive migration actually require it, rather than built speculatively now.
- **Running `alembic upgrade head` at web-process startup.** Rejected: this project's own `ADR-008` already established that application startup never owns schema mutation (`Base.metadata.create_all()` was rejected there for the identical reason: no reviewable, ordered history, and no way to reason about what changed). A startup migration additionally risks non-deterministic deploy timing the moment more than one web replica exists, and would make a failed migration indistinguishable from a failed process boot.
- **Failing process startup (crashing) on a schema mismatch, rather than reporting unready.** Rejected: makes a trivially fixable, common condition (this exact incident, or an ordinary local-dev database that is one migration behind) indistinguishable from a genuine code defect in supervision/orchestration logs, and is actively hostile to local development, where a clear, queryable, non-crashing "not ready: schema_mismatch" signal is strictly more useful than a crash loop.
- **A single boolean "healthy" endpoint, rather than a health/readiness split.** Rejected: collapses two genuinely different questions ("is the process alive" vs. "is it safe to route traffic here") into one, exactly the ambiguity that let this incident's own `/health` check report `200` while the application was, in every practically meaningful sense, broken.
- **A second, independently-written compatibility check inside the maintenance worker**, rather than reusing the web route's own function. Rejected: this project has repeatedly (release-processing locking, the observation-classification helper, `Since Last Visit`'s watermark logic) preferred one shared implementation over two independently-evolving ones whenever the underlying fact being checked is genuinely the same fact — a schema-compatibility check is exactly that shape.
- **Giving `process_release.py` a new exit code `2` to match `run_maintenance.py`'s own convention.** Rejected: `process_release.py` has never had a distinct fatal/configuration exit code — every operational failure there has always returned `1`. Introducing a new value for one new case, inconsistent with 100% of that file's own existing, already-tested exit codes, would be a larger, less consistent change than reusing its own established convention.

## Why This Decision

Exact equality is the smallest correct policy for a project with no rolling-deploy story yet, and it is explicit about exactly when it stops being correct — the decision names its own expiration condition (§32 of the product contract) rather than presenting itself as permanent. Deriving the expected revision from the packaged migration files themselves, rather than a duplicated constant, means the check can never drift from what the code actually requires — the two could not disagree even if a future migration were added carelessly. Reusing one function across the web route and both CLIs is what makes "reliable" mean the same thing everywhere in this system: a schema mismatch is caught identically whether a human hits the API or a scheduler invokes the maintenance CLI, rather than three independent opinions about the same fact.

## Consequences / Tradeoffs

- Gains: the exact failure class that produced the #26A incident is now diagnosable without touching the affected database at all — `/readiness` reports it directly, live-proven against the real, still-unrepaired development database this ADR's own incident describes.
- Gains: `/health` remains a trivially cheap, dependency-free liveness check, unaffected by database state — exactly the property a process supervisor needs, now formally distinct from the property a traffic router needs.
- Gains: the maintenance worker can never silently attempt economic processing against a schema it does not recognize — the same guarantee the web route gets, for free, via the shared function.
- Cost: exact equality means an application instance whose own code is objectively "old enough" to work against a strictly newer, backward-compatible schema will still report itself unready — a known, accepted over-strictness for V1 (§8/§9 of the product contract), not a bug.
- Cost: this ADR does not itself make the currently-known-stale development database compatible — remediation (`alembic upgrade head` against that specific database) remains a deliberate, separate, operator-approved action, exactly as it was the first time this failure class occurred.

## Revisit When

- Rolling or blue-green deployment becomes real, or a future migration needs to remove/narrow something an older, still-running application version depends on — at that point, generalize from exact equality to a genuine minimum-compatible-revision range under an expand/contract migration discipline, per the product contract's own §32.
- A real deployment pipeline exists (#26D) — at that point, confirm the pipeline's own migration-apply-then-verify step reuses this exact same compatibility check for its own post-migration verification, rather than a third, independently-written one.
- A genuine need for automated-vs-manual distinction, or for row-level worker claiming, arises for the maintenance CLIs specifically — unrelated to this ADR's own decision, but worth reconfirming this ADR's own preflight-ordering guarantee (compatibility checked before any economic write) still holds under whatever changes.
