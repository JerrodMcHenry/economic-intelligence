# ADR-028: One Reusable Production Container Image Serves Web, Migration, and Operational CLIs; CI Validates Code, It Never Deploys or Migrates

## Status
Accepted

## Context

ADR-027 established schema compatibility checking and the health/readiness split as durable architecture, implemented by Increment #26C. That work made it possible to *detect* an incompatible deployment; it did not yet make deployment itself boring and repeatable. Increment #26D's own job, per `docs/product/production-reliability-deployment-v1.md` (#26B) §12, is the release pipeline this application has never had: build → test → migration preflight → apply migrations once → verify → deploy web → smoke test. Two questions had to be answered to build that pipeline at all: how is this application packaged so the same code version can run as a web server, a migration command, and the existing operational CLIs without drift between them; and, given no CI existed at all (confirmed, #26B §5), whether and how to introduce one without it becoming a second, uncontrolled path to production.

## Decision

**A single Dockerfile builds one production image, reused unmodified for all three of this application's own entry points** — the web server (`uvicorn app.main:app`, the image's own default `CMD`), the new migration command (`python -m app.operations.release preflight|migrate`), and the existing operational CLIs (`python -m app.operations.run_maintenance`, `python -m app.operations.process_release`) — selected at `docker run` time by overriding the command, never by building a second, subtly divergent image. The image installs only this project's own production dependencies (never the `dev` extra), copies no `.env`/`.git`/test artifacts (`.dockerignore`), and accepts a build-time `APP_VERSION` argument so `/readiness`'s own version field never depends on a `.git` directory being present at runtime.

**A new, single, explicit migration command — `app.operations.release` — is the ONE place this application's own database schema is ever advanced**, reusing #26C's own shared `check_schema_compatibility` function for its preflight (never a duplicated check), calling `alembic.command.upgrade(config, "head")` exactly once, and refusing outright (no downgrade, no automatic correction) on `SCHEMA_AHEAD`/`SCHEMA_AMBIGUOUS`. Web-process startup remains, and must continue to remain, completely unaware of it — the same "startup never mutates schema" boundary ADR-027 already established, now proven against a second call site.

**Continuous integration is introduced (GitHub Actions, `.github/workflows/ci.yml`), scoped to validation only.** It runs the existing backend and frontend test/typecheck/lint/build suites against an ephemeral, CI-local PostgreSQL service container — never a production database, never a production credential (no `secrets.` reference anywhere in the workflow; FRED/OpenAI calls remain fully mocked, exactly as the existing test suite already requires). **It contains no deploy job, and it never invokes `app.operations.release`, `run_maintenance`, or `process_release`.** The actual release pipeline (migrate → deploy → smoke test) is deliberately left as a platform-neutral command sequence a *future* deployment system invokes, not something this CI workflow triggers on push — because no hosting platform has been chosen yet (§42), inventing a deploy step now would either be fake or would force a premature hosting decision.

## Alternatives Considered

- **Separate images for web, migration, and maintenance.** Rejected: the explicit anti-pattern #26B's own primary goal warns against ("avoid separate subtly divergent images") — three images built from the same source at slightly different times can drift in dependency versions or code state in a way one image, selected by command override, structurally cannot.
- **A CI workflow that also deploys on push to main.** Rejected: no hosting platform is chosen (§42, deliberately, still platform-neutral); a deploy step with nothing real to deploy to would either be inert (misleading) or would force a hosting decision as a side effect of a testing increment, exactly the premature-coupling this project has repeatedly avoided elsewhere (e.g. ADR-024's own scheduler/orchestrator separation, chosen for the identical reason).
- **Running `alembic upgrade head` directly inside the migration command's own subprocess shell-out, mirroring the test suite's own `_apply_migrations` fixture pattern.** Rejected in favor of calling `alembic.command.upgrade` directly from Python: the fixture's subprocess approach exists specifically to point at a *different* database than the process's own configured one (a test database); production's own migration command always wants the process's own already-configured `DATABASE_URL` (already wired via `app/core/config.py`, already read by `alembic/env.py` itself), so a direct Python call is simpler and has one fewer moving part, with no offsetting benefit from shelling out.
- **A dedicated migration-only database role, separate from the application's own runtime role.** Considered (per #26B §46) and explicitly deferred again: still not justified before a real production database and a real operator team exist; named in the runbook as a public-beta-tier hardening step, not built now.
- **An explicit Postgres advisory lock around the migration step.** Considered (per #26D's own source prompt §21) and rejected for now: #26B's release process is already a single, serialized pipeline phase by design, this project has no concurrent-deploy-triggering mechanism today, and Postgres's own transactional DDL already fails loudly (not silently) on a genuinely conflicting concurrent attempt. Recorded as a named "revisit when" in `app/operations/release.py`'s own docstring, not built reflexively.

## Why This Decision

One image selected by command override is the smallest mechanism that guarantees "the exact same code version" is genuinely true across web, migration, and maintenance — a property that matters specifically because this application's own correctness now explicitly depends on code and schema staying in agreement (ADR-027). Scoping CI to validation-only, with zero path to production baked in, keeps testing infrastructure and deployment infrastructure decoupled exactly the way #26B's own core principle already separated "does the code work" from "is this specific instance safe to serve" — introducing CI should not quietly become the project's first, accidental deployment mechanism.

## Consequences / Tradeoffs

- Gains: a genuinely repeatable, single-artifact release process exists for the first time in this project's history, verified end-to-end against real PostgreSQL (every migration-state transition the compatibility checker can classify, exercised by `python -m app.operations.release` directly, not merely asserted).
- Gains: CI catches regressions (including deliberately, in the migration chain itself, since the full test suite already exercises fresh-to-head and previous-to-head migrations) before any release process would ever run against a real target.
- Cost: the Dockerfile was written and reviewed carefully but is **not build-verified in this project's own development environment** (no Docker daemon available where this increment was implemented) — honestly disclosed, not papered over; verifying a real `docker build`/`docker run` is a named, explicit follow-up for whichever environment first has Docker available.
- Cost: this ADR does not choose a hosting platform, so the release command it establishes is exercised today only directly (by an operator, or by this project's own tests) — a real CI/CD pipeline invoking it automatically remains future work, not yet built.

## Revisit When

- A concrete hosting platform is chosen — at that point, confirm the single-image, command-override model maps cleanly onto that platform's own deployment primitive (a scheduled job, a release-phase hook, or equivalent) without needing a second image.
- Docker becomes available in whatever environment next touches this repository — at that point, perform the real `docker build`/`docker run` verification this ADR's own image was written for but could not exercise, and correct anything a live build reveals.
- A genuinely concurrent-deploy-capable pipeline exists — at that point, revisit whether the migration step still needs no advisory lock, per `app/operations/release.py`'s own already-recorded reasoning.
- Multiple, genuinely concurrent operators or automated deploy triggers become real — at that point, reconsider whether CI should gain any deploy-adjacent responsibility at all, rather than assuming today's validation-only scope remains correct forever.
