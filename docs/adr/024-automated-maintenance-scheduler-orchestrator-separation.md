# ADR-024: Automated Release-Processing Maintenance Separates Scheduler From Orchestrator, and Reuses the Existing Deterministic CLI Rather Than an In-Process Scheduler or a Public HTTP Trigger

## Status
Accepted

## Context

Through Increment #24, release processing (`app.services.release_processing.ReleaseProcessingService`, #18/#20D.2) was deliberately, exclusively manual: an operator runs `python -m app.operations.process_release --occurrence-id <id>` by hand. #25A's own product/retention audit found this is the single largest gap standing between the current product and an honest "continuously maintained" claim, and the strongest candidate retention feature (Since Last Visit) depends on it for its own honesty. #25B's own operational-design contract freeze (`docs/product/automated-economic-maintenance-v1.md`) resolved the resulting design questions; this ADR records the one decision from that document durable enough, and consequential enough for future work, to need its own record — mirroring this project's own established practice of writing an ADR for a boundary decision, not for every operational detail (see ADR-009's repository boundary, ADR-016's discovery-sync boundary, ADR-019's release-calendar independence).

This project has no deployment/hosting story at all (confirmed directly: `pyproject.toml` declares no job-queue, scheduler, or background-worker dependency of any kind — no Celery, no Redis, no APScheduler; no `Dockerfile`/`Procfile`/`docker-compose.yml` exists anywhere in the repository). Any automation design had to be chosen without assuming a specific future hosting environment.

## Decision

**Automated maintenance is split into two structurally independent halves that must never be coupled: a SCHEDULER (external, swappable, owns only *when* code runs) and an ORCHESTRATOR (`app.services.maintenance.MaintenanceOrchestrator`, owns *what* due work exists and processes it). The orchestrator is invoked through a new, additive, one-shot CLI entry point (`python -m app.operations.run_maintenance`) that runs exactly one bounded sweep and terminates — it never loops, never sleeps, and never schedules itself.** Concretely:

- No in-process scheduler (e.g. an APScheduler-style startup hook inside `app.main`) was added. `app/main.py` has, and must continue to have, zero awareness of maintenance (checked structurally: `tests/test_maintenance_architecture.py::TestNoInProcessScheduler`).
- No public HTTP endpoint triggers release *processing*. The existing, deliberately unauthenticated `POST /api/v1/releases/sync` endpoint (release *calendar* sync — idempotent metadata only) is unaffected and untouched; release processing's own external-provider-request-and-canonical-write shape remains off the public HTTP surface entirely, exactly as `app/operations/process_release.py`'s own pre-existing docstring already committed to for the manual path (checked structurally: `tests/test_maintenance_architecture.py::TestNoPublicMaintenanceMutationEndpoint`).
- The orchestrator discovers due occurrences via one new, narrowly-scoped read query (`ReleaseProcessingRepository.list_due_occurrence_ids`) and processes each individually by calling the EXISTING, completely unmodified `ReleaseProcessingService.process_occurrence` — through a new, shared, lock-acquiring wrapper (`try_acquire_and_process_occurrence`) that both the automated path and the existing manual CLI now call, so the two paths can never diverge in safety (checked structurally: `tests/test_maintenance_architecture.py::TestOccurrenceLockingIsStructural`).
- Concurrency safety uses a PostgreSQL transaction-scoped advisory lock (`pg_try_advisory_xact_lock`, keyed by occurrence id) — zero schema change, automatically released on commit or rollback (including an unhandled crash), never requiring an explicit unlock call that could leak.
- Sweep-level operational health (did the orchestrator itself run, and with what due/processed/failed counts) is recorded in a new, small, separate table (`maintenance_sweeps`) — deliberately never the same table or concept as `ReleaseCheckRun` (per-occurrence, economic-check-shaped data), so "did the worker run" is never conflated with "was a specific occurrence's own check successful."

## Alternatives Considered

- **An in-process scheduler (APScheduler or equivalent) started at FastAPI's own web-process startup.** Rejected: couples release processing's own lifecycle to the *web* process's lifecycle (restarts, redeploys), and — critically, given this project's own undecided future hosting model — any future horizontal scaling to multiple web worker processes would silently multiply the scheduler itself, self-inflicting the exact concurrency risk the advisory lock exists to prevent.
- **A dedicated `POST /maintenance/run` (or similar) HTTP endpoint, triggered by an external scheduler over HTTP.** Rejected: would require either inventing a new authentication mechanism (this project has none, anywhere, by prior explicit design) or accepting an unauthenticated public endpoint that issues external provider requests and canonical database writes — precisely the risk this project already refused once, explicitly, when it chose the manual CLI's own shape for #18.
- **Extending the existing single-occurrence CLI (`process_release.py`) with a "process all due occurrences" mode, rather than a new, separate script.** Considered and rejected in favor of a new script: the existing CLI's own explicit, single-occurrence, operator-facing shape (`--occurrence-id` required) is itself a deliberate #18 decision worth preserving unmodified for manual/recovery use; a new, additive entry point keeps that shape stable while cleanly introducing the new "discover and process everything due" behavior as its own, separately testable unit.
- **Row-level occurrence claiming (a `claimed_by`/`claimed_at` column) instead of a PostgreSQL advisory lock.** Rejected for V1: requires a migration, and only becomes valuable once multiple, distributed concurrent workers need observability into "who is working on what" — not this project's actual deployment shape (a single external scheduler invoking a single script instance is the expected shape); the advisory lock alone already prevents unsafe concurrent processing without that added schema and complexity.
- **Bundling minimal recorded-canonical-state persistence into this same increment**, since automation's own before/after evidence computation already produces exactly the value such a snapshot would need. Rejected: explicitly deferred to its own future, dedicated contract-freeze increment (`docs/product/automated-economic-maintenance-v1.md` §35/§42/§43) — mirroring this project's own repeatedly-successful discipline of never folding a persistence-shaped decision into an already-large adjacent increment, and because the marginal delay cost of deferring it one further increment is small and bounded, not months.

## Why This Decision

The scheduler/orchestrator split is the one choice every future deployment-model decision (local cron today, a platform's own scheduled-task feature tomorrow, or anything else) must remain compatible with — getting it wrong now would mean re-litigating locking, transaction boundaries, and due-work semantics a second time once a real hosting environment is finally chosen. Reusing `ReleaseProcessingService.process_occurrence` completely unmodified, through one shared, lock-aware entry point rather than two independently-evolving call paths, is the same "never a second, informal implementation" discipline ADR-022 already applied to release processing's own analytical logic, restated here for its *invocation* path instead of its *economic* logic.

## Consequences / Tradeoffs

- Gains: the scheduling mechanism can change freely in the future (a developer's own local cron today, a platform's scheduled-task feature tomorrow, or anything else) without ever touching the orchestrator's own stable, tested logic — no economic or safety semantics anywhere depend on which scheduler is in use.
- Gains: the manual and automated paths can never silently diverge in locking behavior, since both call the identical shared wrapper — there is no "safe automatic path and unsafe manual bypass" to accidentally create later.
- Gains: a crash at any point during automation inherits release processing's own pre-existing, already-strong crash-safety guarantee (one transaction per occurrence, `session_scope`'s own commit-once-or-rollback discipline) for free, because the orchestrator was deliberately built never to batch multiple occurrences into one shared transaction.
- Cost: a genuine database-layer failure while processing one occurrence still, as before #25C, leaves no `ReleaseCheckRun` row for that specific attempt — the sweep's own in-memory accounting and structured log output is the only surviving evidence for that occurrence, a real, named, accepted gap (unaffected, not introduced, by this decision).
- Cost: this project still has no genuine hosting/deployment story; this ADR chooses the option that assumes the least about one, but does not itself decide where the external scheduler will eventually run — that remains a separate, later operational decision.

## Revisit When

- This project ever adopts a real deployment/hosting story (a specific PaaS, a container orchestrator, or an in-house scheduler) — at that point, confirm the chosen scheduling mechanism can invoke `python -m app.operations.run_maintenance` on a cadence without requiring any change to the orchestrator itself; if it cannot, that is evidence the orchestrator's own CLI-shaped boundary needs revisiting, not evidence to compromise the scheduler/orchestrator separation.
- Multiple, genuinely distributed concurrent workers become a real requirement (not merely a theoretical possibility) — at that point, revisit whether the transaction-scoped advisory lock alone remains sufficient, or whether row-level claiming (with real "who is working on what" observability) is now justified.
- The deferred recorded-canonical-state persistence increment is eventually designed — at that point, its own write must occur inside the same transaction as the successful analysis recomputation it describes (a hard constraint already frozen forward in `docs/product/automated-economic-maintenance-v1.md` §41), and its own contract-freeze turn should re-confirm this ADR's own boundary still holds rather than assuming it.
