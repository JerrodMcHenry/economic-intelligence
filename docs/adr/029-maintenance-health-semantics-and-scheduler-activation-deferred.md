# ADR-029: Maintenance-Worker Health Is Classified From `MaintenanceSweep` Evidence Alone With Five States; Scheduler Activation Is Deliberately Deferred, Not Fabricated

## Status
Accepted

## Context

ADR-024 established that automated maintenance is triggered by an external scheduler invoking a one-shot CLI, with sweep-level operational health recorded separately from any individual occurrence's own outcome (`MaintenanceSweep`, distinct from `ReleaseCheckRun`). Through Increment #26D, that evidence existed but was never queried by anything — an operator had no way to ask "is the maintenance worker actually healthy" without reading raw SQL. `docs/product/production-reliability-deployment-v1.md` (#26B) §26/§54 named the requirement (a heartbeat query, staleness detection, a distinction between "the worker crashed" and "the worker simply hasn't been asked to run again yet"); Increment #26E is the resulting implementation, governed by an explicit truthfulness requirement this ADR treats as load-bearing, not rhetorical: code existence is not automation, a scheduler configuration file is not automation, and a successful manual invocation is not automation.

## Decision

**A pure domain module (`app.domain.maintenance_health`) classifies maintenance-worker health into exactly five states — `HEALTHY`, `DEGRADED`, `STALE`, `UNFINISHED`, `NEVER_RUN` — derived entirely from two facts read from `MaintenanceSweep`: the single most recent sweep regardless of completion, and the single most recent sweep that has actually finished.** Concretely:

- **`NEVER_RUN` is not a failure state in the operational sense — it is the expected, honest answer before a scheduler is ever activated**, and must never be presented to an operator as equivalent to "the scheduler used to work and stopped." It is derived identically whether zero sweeps exist at all, or the very first sweep is still in progress with no completed evidence yet.
- **A sweep that hasn't finished is not automatically treated as crashed.** Only when the most recent sweep's own `started_at` is older than an operator-tunable grace period (default 30 minutes, derived from — not measured against — the small, typically-fast due-work volume `automated-economic-maintenance-v1.md` §49 already estimated) does it become `UNFINISHED`. Within that window, overall health is judged from the most recent sweep that *has* completed instead — a still-running sweep never masks or discards still-valid, more recent-than-stale evidence from the one before it.
- **Staleness is measured from `started_at`, never `finished_at`**, because staleness answers "has the worker attempted to run recently," which only the attempt time answers directly — the default threshold (3 hours) is three times the shortest end of the already-frozen hourly-order cadence, giving real tolerance for scheduler jitter without masking a scheduler that has genuinely stopped.
- **`DEGRADED` is a distinct state from `STALE`/`UNFINISHED`**: a sweep that completed recently but recorded `failed_count > 0` means the *worker* is functioning correctly — the failure is in one or more individual occurrences' own provider/processing outcome, a fact `MaintenanceSweep` already, correctly, keeps separate from worker-level health (ADR-024's own "worker health and economic freshness are two separate concepts" rule, extended here one level further: worker health and *occurrence-level* processing success are also kept separate).
- **Schema compatibility is checked first, unconditionally, before any sweep evidence is interpreted at all** — reusing #26C's own shared `check_schema_compatibility`, never a duplicated check — because sweep history read against an incompatible schema cannot be trusted to mean what it appears to mean.
- **No sweep-level advisory lock is added.** Occurrence-level locking (ADR-024) already prevents the one dangerous outcome (duplicate audit rows for one occurrence); two overlapping full sweeps remain theoretically possible but operationally implausible given the cadence-to-duration ratio, and no observed problem justifies the added complexity now — named explicitly as a deferred, not overlooked, decision.
- **No persisted distinction between a manually-triggered and a scheduler-triggered sweep is added.** Per the identical reasoning already applied once to `RecordedMonitorResult` (#25D/ADR-025: no processing-origin field, because no identified product requirement needs it), origin is left to scheduler/platform-level execution logs, not a new schema column.
- **Scheduler activation itself is explicitly deferred, not fabricated.** A reviewable GitHub Actions template exists (`.github/workflows/scheduled-maintenance.yml.disabled`) — syntactically valid, invoking the exact, unmodified production maintenance command on the frozen cadence, referencing secrets by name only — but is named with a `.disabled` suffix specifically so GitHub Actions cannot recognize or execute it, on any trigger, regardless of its own content. Activation requires a real, network-reachable production database and an explicit, reviewed answer to whether a scheduler can reach it without weakening its own access controls — neither exists yet, and this ADR records that as a real, current blocker, not a gap papered over by the template's mere presence.

## Alternatives Considered

- **A single boolean "is maintenance healthy" instead of five states.** Rejected: collapses "never activated" (expected), "worker crashed" (needs investigation), "worker fine, one occurrence failed" (different remediation), and "scheduler stopped firing" (different remediation again) into one bit, discarding exactly the operationally useful distinctions #26E's own source prompt named explicitly (§23: "latest attempt failed, latest successful run 3 hours ago" is useful information a single value would lose).
- **Treating any unfinished sweep as immediately unhealthy.** Rejected: a sweep that started 30 seconds ago and hasn't finished is not evidence of a problem — it is evidence the worker is, right now, doing its job. Flagging it as broken would train an operator to ignore the status output, defeating its own purpose.
- **Activating the GitHub Actions scheduler now, against a placeholder or a locally-reachable database, to demonstrate the pipeline end-to-end.** Rejected as a form of the exact fabrication this increment's own truthfulness requirement prohibits: a scheduled workflow that "works" against a database no real production traffic will ever touch, or against a database made publicly reachable purely to let a GitHub-hosted runner reach it, would either prove nothing about real activation or would weaken a database's own access controls solely for demonstration purposes — explicitly rejected by the source prompt's own §44 ("do not weaken production DB access controls merely to make scheduler convenient").
- **Persisting a `processing_origin`/`triggered_by` column on `MaintenanceSweep`.** Rejected for the same reason #25D already rejected the analogous field on `RecordedMonitorResult` — no identified product requirement needs the distinction, and scheduler/platform execution logs already carry it for free when it does matter.
- **A sweep-level Postgres advisory lock, added preemptively.** Rejected for now, per this project's own repeated "do not add locking reflexively, document the reasoning" discipline (most recently applied identically to the migration command's own locking question in Increment #26D) — named as a revisit-when item, not built speculatively.

## Why This Decision

Five states is the smallest vocabulary that lets an operator distinguish every remediation path this system can actually be in, without inventing a distinction the persisted evidence cannot actually support (there is no sixth state for "the scheduler is configured but has bad credentials," for instance — that surfaces as `NEVER_RUN` or a job-level failure the scheduler's own logs already show, not something `MaintenanceSweep` evidence alone could ever prove). Refusing to fabricate activation is the direct, literal application of this increment's own governing rule: a `.disabled` file that cannot run is a stronger truthfulness guarantee than a comment promising it won't be triggered, because it does not depend on anyone reading the comment.

## Consequences / Tradeoffs

- Gains: an operator (or a future monitoring integration, via `--json`) can now ask a single, well-defined question — "is maintenance healthy" — and get a specific, actionable answer, for the first time since #25C shipped the underlying evidence.
- Gains: the exact automatic-maintenance claim threshold is now a checkable list (two real scheduled runs, two real `MaintenanceSweep` rows, a `HEALTHY` health-check result), not a judgment call — restated in the runbook precisely so a future increment cannot round "the template exists" up to "the claim is true."
- Cost: this increment does not, and could not honestly, deliver working scheduled automation — that remains blocked on a hosting/security decision this project has not yet made. The runbook and this ADR both state this as a real, current limitation, not a completed capability.
- Cost: the default thresholds (3-hour staleness, 30-minute unfinished-grace) are, like every other operational constant this project has frozen, estimated from the existing cadence contract rather than empirically tuned against real production traffic, which does not exist yet to tune against.

## Revisit When

- A real, network-reachable production database exists and its own network/access-control posture has been reviewed against GitHub-hosted runner IP ranges (or a self-hosted runner is placed inside that same network) — at that point, follow the template's own activation checklist, and only then may the "automatically maintained" claim be made, per the threshold this ADR and the runbook both restate.
- Real scheduled-run history accumulates — at that point, revisit whether the 3-hour/30-minute default thresholds actually match observed sweep duration and cadence jitter, rather than assuming the estimate was exactly right.
- Genuine evidence of overlapping sweeps causing confusing `MaintenanceSweep` history appears — at that point, add the sweep-level advisory lock this ADR deliberately deferred, following the same `pg_advisory_lock` pattern already used elsewhere in this project.
- A real operator team or a genuine need to distinguish manual-vs-scheduled sweep origin emerges — at that point, reconsider the no-new-column decision against that specific, concrete need, not speculatively.
